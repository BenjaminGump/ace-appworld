## STRATEGIES AND HARD RULES
[shr-00001] Make sure to end code blocks with ``` followed by a newline(\n).
[shr-00005] Always look at API specifications (using apis.api_docs.show_api_doc) before calling an API.
[shr-00006] Write small chunks of code and only one chunk of code in every step. Make sure everything is working correctly before making any irreversible change.

[shr-00107] When a task requires an irreversible destructive action (e.g., account termination/deletion) AFTER a backup or export, always follow this strict sequence: (1) complete the backup/export, (2) verify the backup programmatically (e.g., read the file back, assert row counts, check content), (3) only then perform the irreversible action. Never perform the destructive action before the backup is verified — if the backup is incomplete or corrupted, the data will be permanently lost. This extends [shr-00006] to the specific case of backup-then-destroy tasks.
## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00012] The phone app's `search_contacts` API has a `relationship` filter parameter (e.g., relationship='roommate') that can be used to authoritatively identify contacts by their relationship type. Always use this filter rather than guessing or searching by name.
[api-00013] The file_system app's `show_directory` API has a `substring` filter parameter that searches file and directory names (case-insensitive). Use this to quickly find specific files (e.g., substring='electricity' to find bill files) instead of manually browsing directories.
[api-00019] The spotify `show_recommendations` API returns only basic song info (song_id, title, album_id, album_title, duration, artists) and does NOT include genre or release_date. When you need to filter recommended songs by genre or release year, you must call `show_song` for each recommended song to retrieve full details including `genre` and `release_date`.
[api-00022] When a task references 'MY' usage data (e.g., 'least-played in MY library', 'most-listened by ME', 'my play count'), always check for user-private APIs (e.g., `show_song_privates`, `show_album_privates`, `show_playlist_privates`) that may contain user-specific metrics. Do NOT rely on global public metrics from `show_song` or `show_album` (e.g., global `play_count`, global `like_count`), as these reflect platform-wide data, not the user's personal activity. The correct workflow: collect all item IDs from the library → call the corresponding `show_*_privates` API for each → find min/max by the user-specific metric.
[api-00025] The spotify `show_song_library` and `show_playlist` APIs return only basic song info (song_id, title, album_id, etc.) and do NOT include `release_date` or `genre`. When you need to filter library or playlist songs by release year or genre, you must call `show_song` for each song to retrieve full details. To avoid redundant API calls when the same song may appear in both the library and multiple playlists, build a shared cache dict (e.g., `song_cache = {}`) mapping song_id → song_details, and check the cache before calling `show_song`.
[api-00027] The spotify `show_playlist_library` API response already includes a `song_ids` list (array of integers) for each playlist. When you only need song IDs (e.g., to compute total playlist duration by looking up each song's `duration` via `show_song`), you can skip the intermediate `show_playlist` calls entirely and use `song_ids` directly from the `show_playlist_library` response. Only call `show_playlist` if you need playlist-level details not present in the library listing (e.g., `shareable_link`).
[api-00029] When a task references 'songs I have liked' or 'my liked songs', use the `show_liked_songs` API — NOT `show_song_library` (which returns songs saved to the library, a different concept). The `show_liked_songs` response already includes an `artists` list (with `id` and `name`) for each song, so you do NOT need to call `show_song` separately to get artist information. Similarly, `show_liked_albums` and `show_liked_playlists` exist for liked albums/playlists respectively.
[api-00031] The spotify `show_song_queue` API returns songs with `position` (integer starting at 0), `is_playing` (boolean), and `is_current` (boolean) fields. When a task references 'songs played so far' in the queue, interpret this as all songs from position 0 up to and including the current song (identified by `is_current: true`). Songs at positions after the current song have NOT been played yet. Use `show_current_song` as an alternative to find the current song's ID, but `show_song_queue` gives you both the full queue and the current position in one call.
[api-00032] The spotify `search_artists` API supports filtering by `genre` (string, must match exact genre from `show_genres`), `min_follower_count` (integer), and `max_follower_count` (integer) parameters. When a task requires finding artists by genre or follower threshold (e.g., 'reggae artists with at least 21 followers'), use these filters directly in a single paginated call rather than retrieving all artists and filtering client-side. The response includes `artist_id`, `name`, `genre`, `follower_count`, and `created_at` for each artist.
[api-00040] The phone app's `search_text_messages` and `search_voice_messages` APIs with the `phone_number` parameter return ALL messages exchanged WITH that contact — both messages where the contact is the sender AND messages where the contact is the receiver (i.e., messages the user sent TO that number). This is bidirectional. When a task specifies directionality (e.g., 'messages FROM 9294880327'), you must filter the results by the `sender` field: `msg['sender']['phone_number'] == '9294880327'`. Do NOT assume the `phone_number` filter only returns messages from that number. The response schema includes both `sender` and `receiver` objects with `phone_number` fields — use these to apply directional filtering before taking action.
[api-00043] When filtering Venmo social feed transactions that 'involve' a specific person (e.g., 'transactions involving my roommates'), you must check BOTH the `sender` and `receiver` email fields. A transaction involves a person if they are either the sender OR the receiver. Use case-insensitive email matching against a set of target emails: `if tx['sender']['email'].lower() in target_emails or tx['receiver']['email'].lower() in target_emails`. Do not filter by sender only, as this will miss transactions where the target person is the receiver.
[api-00044] The spotify app has two distinct artist-following APIs: `show_artist_following` (singular) checks if the user follows ONE specific artist (requires `artist_id`, returns `{following: boolean}`), while `show_following_artists` (plural) lists ALL artists the user follows with pagination (returns `artist_id`, `name`, `genre`, `follower_count`, `followed_at`). When you need to enumerate all followed artists (e.g., for bulk unfollow operations), always use `show_following_artists` (plural) with pagination — do NOT iterate over artist IDs calling `show_artist_following` one at a time.
[api-00047] The Venmo `show_transactions` API has a `user_email` filter parameter that, when passed, only returns transactions between you and the user with that email address. When you need to find transactions with specific people (e.g., roommates), use `user_email` per person rather than fetching all transactions and filtering client-side. This is more efficient and reduces the risk of missing transactions due to client-side filtering errors. Combine with `direction='sent'` and `min_created_at` for date-range and direction filtering.
[api-00048] The spotify `show_album_library` API response already includes a `song_ids` list (array of integers) for each album, similar to `show_playlist_library`. When you only need song IDs from albums in the library (e.g., to find songs that are both in the album library AND liked), you can skip the intermediate `show_album` calls entirely and use `song_ids` directly from the `show_album_library` response. Only call `show_album` if you need album-level details not present in the library listing.
[api-00050] The Venmo `show_sent_payment_requests` API does NOT support a `user_email` filter parameter (unlike `show_transactions`). When you need to find sent payment requests for a specific person, you must paginate through ALL sent requests and filter client-side by `receiver['email']` (case-insensitive). Do not assume `user_email` filtering is available on this endpoint just because `show_transactions` supports it.
[api-00055] The Venmo `approve_payment_request` API has an optional `payment_card_id` parameter. If not passed, the approval draws from your Venmo balance by default. If you need to use a specific payment card instead, pass the `payment_card_id` (obtainable via `show_payment_cards`). When approving multiple requests in bulk, decide upfront whether to use balance or a card and apply consistently.
[api-00058] The spotify `show_song` API returns a `duration` field that is in SECONDS (integer), even though the API doc does not explicitly state the unit. When a task asks for duration in minutes, divide the total seconds by 60 and use `round()` for nearest-integer rounding. For example, 1964 seconds / 60 = 32.73 minutes, rounded to 33.
[api-00063] The Venmo `show_social_feed` API response does NOT include a `liked_by_me` field, so you cannot pre-check whether the current user has already liked a transaction before calling `like_transaction`. Unlike the check-before-act principle in [misc-00030]/[misc-00056], pre-checking is not feasible here. Instead, rely on the `like_transaction` API's idempotent behavior (it succeeds even if already liked) and verify post-action by confirming `like_count` increased by 1 for each target transaction.
[api-00066] The Venmo `show_sent_payment_requests` API response does NOT have a `status` field. Instead, the status is inferred from two timestamp fields: `approved_at` (null = not approved) and `denied_at` (null = not denied). A request is 'pending' when both are null, 'approved' when `approved_at` is not null, and 'denied' when `denied_at` is not null. Do NOT attempt to access `req['status']` — it will raise a KeyError. The response fields are: `payment_request_id`, `amount`, `description`, `created_at`, `updated_at`, `approved_at`, `denied_at`, `private`, `sender` (with `name` and `email`), and `receiver` (with `name` and `email`).
[api-00068] When a task asks for the 'most played song by [artist] on Spotify' (or similar global metrics about an artist's songs, WITHOUT referencing 'MY' or 'ME'), use the `search_songs` API with the `artist_id` filter. The response already includes `play_count` (and `like_count`, `rating`) directly, so no additional `show_song` calls are needed. This is the inverse of [api-00022]: global public metrics from `search_songs` are correct when the task does NOT reference personal usage. Always paginate through all results and use `max()` over the full dataset per [cms-00052].
[api-00070] The file_system `show_directory` API returns absolute file paths (e.g., `/home/christina/bills/cable/2023-04.txt`). The `show_file` API accepts BOTH absolute paths (starting with `/`) and relative paths (starting with `~/`). When passing paths returned by `show_directory` to `show_file`, you can pass them directly without any conversion — do NOT hardcode path replacements like `file_path.replace('/home/christina', '~')` as this is fragile and relies on knowing the user's home directory name.
[api-00078] The file_system `compress_directory` API has a `delete_directory` parameter (boolean, default=False) that deletes the source directory after compression in a single atomic call. When a task requires compressing a directory AND deleting the original, always use `delete_directory=True` rather than calling `compress_directory` followed by `delete_directory` separately — this avoids inconsistent states if the second call fails. Also pass `overwrite=True` to handle re-runs gracefully (prevents errors if the zip file already exists). Example: `apis.file_system.compress_directory(access_token=token, directory_path=dir_path, compressed_file_path='~/output.zip', delete_directory=True, overwrite=True)`.
[api-00086] The Venmo `show_received_payment_requests` API DOES support a `status` filter parameter (values: 'pending', 'approved', 'denied'), unlike `show_sent_payment_requests` which does NOT have a status field at all (per [api-00066]). When you need to find pending received requests, use `status='pending'` directly in the API call rather than fetching all and filtering client-side. The response schema is the same as `show_sent_payment_requests` (uses `approved_at`/`denied_at` timestamp fields, no `status` field in the response body). Since these are requests received FROM others, filter by `sender['email']` to match specific people (e.g., friends/roommates).
[api-00087] The file_system `show_directory` API returns a list of absolute path STRINGS (e.g., `['/home/adrian/pictures/vacations/bali/', '/home/adrian/pictures/vacations/maui/']`), NOT objects with metadata fields. When you need to extract directory or file names from these paths for use in subsequent operations (e.g., building output file paths like `~/pictures/vacations/<name>.zip`), always parse them programmatically: `names = [path.strip('/').split('/')[-1] for path in directory_paths]` or `import os; names = [os.path.basename(p.rstrip('/')) for p in directory_paths]`. Do NOT visually inspect the printed paths and hardcode the observed names in the next code block — this violates [cms-00023] and breaks if the directory contents change between runs.
[api-00096] The spotify `show_song_privates` API returns ONLY boolean fields (`liked`, `reviewed`, `in_song_library`, `downloaded`) and does NOT contain `play_count` or any numeric usage metric. When a task references 'most listened to' or 'play count' and you check `show_song_privates` per [api-00022], finding no play_count there means you should fall back to the global `play_count` from `show_song`. Do NOT assume a user-specific play count exists just because a private API exists — verify the response schema first.
[api-00098] The spotify `show_downloaded_songs` API returns a list of downloaded songs with fields: `song_id`, `title`, `album_id`, `album_title`, `duration`, `artists` (list with `id` and `name`), and `downloaded_at` (timestamp). It supports `query`, `min_downloaded_at`, `max_downloaded_at`, `page_index`, `page_limit`, and `sort_by` parameters. When a task references 'downloaded songs' or 'songs I have downloaded', use this API — NOT `show_song_library` or `show_liked_songs`. Collect all downloaded song IDs into a set (e.g., `downloaded_song_ids = set(s['song_id'] for s in downloaded_songs)`) for efficient membership testing when checking compound conditions like 'liked AND downloaded'.
[api-00100] The spotify `like_song` API is idempotent — it succeeds even if the song is already liked (returns `{'message': 'Song liked.'}`). While the check-before-act principle from [misc-00030] is still good practice to avoid unnecessary API calls, if you need to like a large batch of songs and want to minimize calls, you can skip the individual `show_song_privates` checks and call `like_song` directly for all target songs. This is analogous to Venmo's `like_transaction` idempotency per [api-00063].
[api-00101] When you need to check the like status of MULTIPLE songs (e.g., before bulk-liking), use `show_liked_songs` with pagination to build a set of liked song IDs (e.g., `liked_song_ids = set(s['song_id'] for s in all_liked_songs)`) rather than calling `show_song_privates` individually for each song. This reduces N+1 API calls to a single paginated call. Then filter: `songs_to_like = [sid for sid in target_ids if sid not in liked_song_ids]`. This is especially useful when the target set is large (e.g., all songs in a queue or playlist).
[api-00102] When the file_system `show_file` API returns binary content (e.g., `'binary:aa6b3b2254...'`) for PDF or other non-text files, do NOT give up on reading the file. Try the `decompress_file` API on the file path — PDFs and other binary files in AppWorld may be stored as compressed files that can be decompressed to reveal text content. Example: `apis.file_system.decompress_file(access_token=token, file_path='~/bills/internet/2023-05.pdf', output_path='~/bills/internet/2023-05_decoded.txt')`, then read the decompressed file with `show_file`. If `decompress_file` fails, explore other file_system APIs or parsing strategies before concluding the content is unreadable.
[api-00105] The spotify `search_albums` API response already includes a `song_ids` list (array of integers) for each album, similar to `show_album_library` per [api-00048]. When you find the target album via search and need its song IDs (e.g., to look up each song's `play_count` via `show_song`), extract them programmatically from the matched album object: `target_album = next(a for a in albums if a['title'].lower() == 'velvet underground'); song_ids = target_album['song_ids']`. Do NOT call `show_album` separately just to get song IDs, and do NOT hardcode the IDs from visually inspecting the search output (violates [cms-00023]).
[api-00106] When a task contains the word 'my' or 'ME' but it modifies a noun OTHER than the metric being queried (e.g., 'most-liked song in MY playlists' — 'my' modifies 'playlists', not 'liked'; 'highest-rated album in MY library' — 'my' modifies 'library', not 'rated'), the metric in question is a GLOBAL public metric, NOT personal usage data. Use the global `like_count`, `play_count`, or `rating` from `show_song`/`show_album` directly — do NOT invoke user-private APIs (e.g., `show_song_privates`) for the metric. This refines [api-00022]: 'my' triggers the private-API check ONLY when it directly modifies the usage metric (e.g., 'MY play count', 'songs I have played most'), not when it merely indicates ownership of the container (e.g., 'in MY playlists', 'in MY library').
[api-00108] The file_system `move_file` API has a `retain_dates` parameter (boolean, default=False) that preserves the original file's `created_at` and `updated_at` timestamps after the move. When organizing files by date-based criteria (e.g., moving photos into subdirectories based on creation month), always pass `retain_dates=True` — otherwise the moved files will get new timestamps reflecting the move time, destroying the original creation date metadata. This is critical for tasks where the categorization logic depends on `created_at` fields, as losing the original dates would make verification impossible and break re-runs. Example: `apis.file_system.move_file(access_token=token, source_file_path=src, destination_file_path=dest, retain_dates=True)`.
[api-00111] The spotify `add_to_queue` API can add a song, album, or playlist to the music player song queue. It accepts `song_id`, `album_id`, or `playlist_id` (pass at most one). When a single playlist/album doesn't have enough content to meet a duration or count requirement, call `add_to_queue` with multiple playlist_ids to build a queue whose combined content meets the requirement. Then call `play_music` (with no ID parameter) to start playing the queue. Note: `play_music` with a `playlist_id` will REPLACE the queue with that playlist's songs — to play a combined queue, first clear the queue with `clear_song_queue`, then `add_to_queue` each source, then `play_music()` with no ID to start from the beginning of the queue.

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00010] When splitting a bill 'among my roommates and me' (or similar phrasing), always include yourself in the divisor. For example, 3 roommates + 1 self = 4 people total. Failing to include yourself will result in overcharging each person.
[cms-00011] In Venmo, distinguish between `create_payment_request` (request money FROM others) and `create_transaction` (send money TO others). When the task says 'make requests' or 'request money', use `create_payment_request`, NOT `create_transaction`.
[cms-00016] When a task specifies an exact output format for a message or reply (e.g., 'a list of comma-separated movie titles', 'just the song title'), send exactly that format without adding conversational preamble or extra context. For example, if asked to reply with comma-separated titles, the message should be 'Movie A, Movie B, Movie C' — not 'Here are my recommendations: Movie A, Movie B, Movie C'. Extra text may cause evaluation failures if strict format matching is expected.
[cms-00017] When filtering by a categorical field (e.g., 'genre', 'category'), always verify the exact valid values using a dedicated API (e.g., `show_genres`) before applying string matching logic. Do not assume the field will contain an exact match — use substring matching (e.g., `'classical' in genre.lower()`) as a fallback if the exact string is uncertain.
[cms-00018] When passing IDs between APIs, explicitly cast them to the expected parameter type (e.g., `int(artist['id'])`) to avoid type mismatch issues. APIs may return IDs as strings even when the consuming API expects integers.
[cms-00023] Never hardcode IDs or values from intermediate outputs into subsequent code blocks. Always derive action lists dynamically from variables and data structures (e.g., iterate over `unliked_songs` and check `existing_reviews` dict) rather than manually copying IDs like `songs_to_create = [31, 173, 202]`. Hardcoding breaks generalizability and risks errors if data changes between steps.
[cms-00028] When parsing or data-processing code fails (e.g., returns an empty list or wrong result), debug and fix the code rather than abandoning it and manually extracting values from the raw output. Manually copying values from intermediate outputs breaks generalizability and risks errors. Instead, inspect the actual data format (e.g., print raw lines to see exact indentation/structure), adjust the parsing logic accordingly, and re-run until it produces correct results programmatically.
[cms-00035] When a task specifies 'last N days (including today)', today counts as day 1 of the N days. Use `timedelta(days=N-1)` to calculate the start date, NOT `timedelta(days=N)`. For example, 'last 10 days including today' with today=2023-06-02 means the range is 2023-05-24 to 2023-06-02 (10 days), so use `timedelta(days=9)`. Using `timedelta(days=10)` would incorrectly create an 11-day window. Always verify boundary dates carefully when filtering by time ranges.
[cms-00036] When filtering by a specific year (e.g., 'released in or before 2021'), extract the year from the ISO date string using string slicing (e.g., `release_date[:4]`) and compare it as a string or integer (e.g., `release_date[:4] <= '2021'`). This is simpler and less error-prone than parsing the full date object with datetime libraries.
[cms-00037] When a task says 'the last X was Y' (e.g., 'the last payment request I sent was approved'), find the most recent X first (by time/date across ALL statuses), then verify it has property Y. Do NOT filter by Y first and then find the most recent among filtered results. These are logically different: the task specifies that the most recent item (by time) has a certain property, not that the most recent item with that property is the one in question. For example, if there was a more recent pending request to the same person, filtering by status='approved' first would incorrectly skip it and select an older approved request.
[cms-00039] When a task references 'this year', 'today', or any relative time concept, do NOT use `datetime.now()` to determine the current date/year. The AppWorld environment may have a simulated time different from the real system clock. Instead, derive the current date/year from API response timestamps (e.g., `created_at` fields from `create_playlist` or `show_playlist`, the `exp` claim in the JWT access token, or any other timestamp returned by an API call). For example, after creating a playlist, use `create_result_or_response['created_at'][:4]` to extract the environment's current year. Using the system clock risks silent failures (e.g., zero results returned) if the environment time and system time diverge.
[cms-00041] When a task says 'from X' (e.g., 'delete messages from 9294880327'), filter by sender identity, not just by contact association. The `phone_number` parameter in phone search APIs returns bidirectional message threads (both sent and received). Always inspect the `sender` field in the response and apply a sender filter (e.g., `[msg for msg in messages if msg['sender']['phone_number'] == target_number]`) to ensure you only act on messages originating from the specified number. Failing to do so may result in over-deletion of messages the user sent TO that number.
[cms-00042] When a note or task contains only first names and you need to perform financial actions (e.g., Venmo payment requests), do NOT search Venmo directly by first name — multiple unrelated users may share that first name. Instead, use the Phone app's `search_contacts` to resolve each first name to a full identity (with email address), then use those exact emails to search Venmo users via `search_users(query=email)`. This ensures you are requesting money from the correct person, especially for contacts with no prior transaction history to cross-reference.
[cms-00046] When returning numeric answers via `apis.supervisor.complete_task(answer=...)`, return a plain number or numeric string (e.g., `1068.0` or `'1068.0'`) without currency symbols, commas, or extra formatting, unless the task explicitly specifies a format. For example, if the task asks 'How much money...', return `1068.0` not `'$1068.00'`. Currency symbols and formatting can cause evaluation failures if strict matching is expected.
[cms-00049] Do NOT attempt to decode JWT access tokens (e.g., using the `base64` module) to extract the `exp` claim or any other metadata — the `base64` module is NOT allowed in the AppWorld environment. While [cms-00039] mentions the JWT `exp` claim as a theoretical source for the current date/year, in practice you cannot decode the token. Instead, always derive the current date/year from API response timestamps (e.g., `created_at` fields from `show_transactions`, `show_playlist`, etc.) by fetching a recent record and reading the timestamp directly.
[cms-00052] Never rely on API sort order + index [0] to find a global maximum or minimum across paginated results. Many APIs (e.g., spotify `search_songs`) apply sorting only 'within each page', so the first element of a concatenated list from multiple pages is NOT guaranteed to be the global max/min. Always collect all pages first, then use `max(list, key=lambda x: x['field'])` or `min(list, key=lambda x: x['field'])` over the full dataset. Also pay close attention to sort direction: `+` prefix means ascending (smallest first), `-` prefix means descending (largest first). Using `+` when you want the maximum will return the minimum at index 0.
[cms-00053] When aggregating data across multiple per-entity queries (e.g., summing transactions for each roommate separately), always deduplicate by tracking unique record IDs in a set before computing the final aggregate. While API filters like `user_email` make duplicates unlikely, defensive deduplication prevents double-counting if the same record appears in multiple query results. For example: `seen_ids = set(); unique_txs = [tx for tx in all_txs if tx['transaction_id'] not in seen_ids and not seen_ids.add(tx['transaction_id'])]`.
[cms-00059] When finding the oldest or newest item by date (e.g., 'oldest released song'), you can compare ISO-format date strings directly using string comparison operators (`<`, `>`) since ISO format (YYYY-MM-DDTHH:MM:SS) sorts lexicographically in chronological order. For example, `if release_date < oldest_date: oldest_date = release_date`. This avoids the need to parse dates with datetime libraries and is simpler and less error-prone. This complements [cms-00036] which covers year extraction via slicing.
[cms-00060] When checking if someone has already paid for a specific event (e.g., a dinner), do NOT rely on description text matching alone — descriptions are user-generated and may vary. Instead, match by expected amount AND date proximity to the event. For example, if the dinner was on 2023-05-19 and the expected share is $28, filter transactions where `tx['amount'] == expected_amount` and `tx['created_at'][:10] == '2023-05-19'`. Also, do NOT simply check for ANY received transaction from a person — coworkers may have prior unrelated transactions (e.g., 'Cookie Baking Night', 'Camping Trip') that would incorrectly flag them as having paid. Always narrow by event-specific criteria (amount + date) before concluding someone has paid.
[cms-00065] When [cms-00060] says to use 'date proximity' to check if someone has already paid for an event, this means checking a DATE RANGE from the event date through today (inclusive), NOT exact date matching. For example, if the dinner was on 2023-05-19 and today is 2023-05-20, use `tx['created_at'][:10] >= '2023-05-19' and tx['created_at'][:10] <= '2023-05-20'` — someone may have paid the day after the event. Using exact date matching (e.g., `tx['created_at'][:10] == '2023-05-19'`) will miss payments made on subsequent days, leading to duplicate payment requests.
[cms-00067] When a task references 'this year' and you are processing data that contains timestamps (e.g., file creation dates, transaction dates), do NOT infer the current year by taking the maximum year from the data (e.g., `max(f['created_at'][:4] for f in files)`). This heuristic assumes the most recent year in the data equals the current year, which can fail if data contains future-dated records or if no records exist from the current year.
