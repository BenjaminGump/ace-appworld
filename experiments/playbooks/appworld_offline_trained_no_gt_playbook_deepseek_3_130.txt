## APIs TO USE FOR SPECIFIC INFORMATION
[api-00004] You can use the "supervisor" app to get information about my accounts and use the "phone" app to get information about friends and family.

[api-00012] The phone app's `search_contacts` API has a `relationship` filter parameter (e.g., relationship='roommate') that can be used to authoritatively identify contacts by their relationship type. Always use this filter rather than guessing or searching by name.
[api-00013] The file_system app's `show_directory` API has a `substring` filter parameter that searches file and directory names (case-insensitive). Use this to quickly find specific files (e.g., substring='electricity' to find bill files) instead of manually browsing directories.
[api-00019] The spotify `show_recommendations` API returns only basic song info (song_id, title, album_id, album_title, duration, artists) and does NOT include genre or release_date. When you need to filter recommended songs by genre or release year, you must call `show_song` for each recommended song to retrieve full details including `genre` and `release_date`.
[api-00021] The Venmo `show_received_payment_requests` API has a `status` filter parameter (values: 'pending', 'approved', 'denied'). Use status='pending' to retrieve only pending requests efficiently, rather than fetching all requests and filtering manually.
[api-00024] The spotify `show_song_library` API returns only basic song info (song_id, title, album_id, album_title, duration, artists, added_at) and does NOT include `play_count`, `like_count`, `genre`, or `release_date`. When you need these fields (e.g., to find the least-played or most-liked song in the library), you must call `show_song` for each song_id retrieved from the library. Note that `show_song` does not require an access_token, so play_count is a global metric, not user-specific.
[api-00026] The spotify `show_playlist_library` API returns `song_ids` (a list of integers) directly in each playlist object. Use these IDs directly rather than calling `show_playlist` for each playlist to retrieve song IDs — this saves unnecessary API calls. However, note that `show_playlist_library` does NOT return song durations, so you still need to call `show_song` for each unique song_id to get the `duration` field.
[api-00032] The spotify `show_liked_songs` API returns artist information directly in each song object (fields: `artists[].id`, `artists[].name`), so you do NOT need to call `show_song` for each liked song to get artist IDs. However, note the field name inconsistency: liked songs use `artists[].id` while `show_following_artists` returns `artist_id` (top-level, not nested). Always check the response schema to use the correct field name when extracting IDs.
[api-00033] The spotify `show_song_queue` API returns songs with `position` (integer), `is_current` (boolean), and `is_playing` (boolean) fields. Songs are played in order in a cycle. When a task references 'songs played so far including the current one', interpret this as all songs from position 0 up to and including the current song's position. Use the `is_current` field to identify the current song's position, then select all songs with `position <= current_position`.
[api-00034] The spotify `search_artists` API supports server-side filtering with `genre` (string), `min_follower_count` (integer), and `max_follower_count` (integer) parameters. Use these built-in filters rather than fetching all artists and filtering manually. Note that `search_artists` does NOT require an `access_token` — it is a public search API. When a task asks for artists by genre and/or follower count (e.g., 'reggae artists with at least 21 followers'), pass genre='reggae' and min_follower_count=21 directly to `search_artists` with proper pagination (page_limit=20).
[api-00043] The phone app's `search_text_messages` and `search_voice_messages` APIs have a `phone_number` parameter that returns the FULL bidirectional conversation thread (both messages sent BY the user TO that number AND messages sent BY that number TO the user). When a task asks to delete or filter messages 'FROM' a specific number, you MUST additionally filter by the `sender` field after fetching: e.g., `spam_messages = [msg for msg in messages if msg['sender']['phone_number'] == '9294880327']`. Do NOT assume the `phone_number` filter returns only messages originating from that number.
[api-00045] The Venmo `show_transactions` API supports server-side filtering with `query` (string, searches transaction descriptions), `min_created_at` (YYYY-MM-DD), `max_created_at` (YYYY-MM-DD), `direction` ('sent' or 'received'), and `user_email` parameters. When looking for specific transactions (e.g., payments for a dinner with a known description), use `query='Friends Dinner'` combined with date filters rather than fetching all transactions and visually scanning. This is both more efficient and more reliable.
[api-00050] The Venmo `show_social_feed` API does NOT support date filtering (no `min_created_at`/`max_created_at` parameters), unlike `show_transactions` which does. When you need to filter social feed transactions by date, you must paginate through the entire feed and filter client-side using `created_at.startswith(today)` (or similar date comparison). Use `page_limit=20` to minimize API calls, but expect potentially large result sets (e.g., 1000+ transactions).

## COMMON MISTAKES AND CORRECT STRATEGIES

[cms-00010] When splitting a bill 'among my roommates and me' (or similar phrasing), always include yourself in the divisor. For example, 3 roommates + 1 self = 4 people total. Failing to include yourself will result in overcharging each person.
[cms-00011] In Venmo, distinguish between `create_payment_request` (request money FROM others) and `create_transaction` (send money TO others). When the task says 'make requests' or 'request money', use `create_payment_request`, NOT `create_transaction`.
[cms-00016] When a task specifies an exact output format for a message or reply (e.g., 'a list of comma-separated movie titles', 'just the song title'), send exactly that format without adding conversational preamble or extra context. For example, if asked to reply with comma-separated titles, the message should be 'Movie A, Movie B, Movie C' — not 'Here are my recommendations: Movie A, Movie B, Movie C'. Extra text may cause evaluation failures if strict format matching is expected.
[cms-00017] When filtering by a categorical field (e.g., 'genre', 'category'), always verify the exact valid values using a dedicated API (e.g., `show_genres`) before applying string matching logic. Do not assume the field will contain an exact match — use substring matching (e.g., `'classical' in genre.lower()`) as a fallback if the exact string is uncertain.
[cms-00018] When passing IDs between APIs, explicitly cast them to the expected parameter type (e.g., `int(artist['id'])`) to avoid type mismatch issues. APIs may return IDs as strings even when the consuming API expects integers.
[cms-00020] When cross-referencing contacts from the phone app with Venmo payment requests (or other app entities), always match by a unique identifier like email rather than name. Names can be ambiguous (e.g., multiple people named 'Smith') or formatted differently across apps. Collect target emails into a set and filter requests by checking if the sender's email is in that set.
[cms-00028] Always inspect sample data values to infer units before performing conversions. For example, Spotify's `show_song` API returns `duration` in seconds (typical values: 200-400 for a 3-6 minute song), NOT in minutes or milliseconds. When a task asks for duration in minutes, divide the sum of durations (in seconds) by 60 and round to the nearest integer.
[cms-00029] When performing bulk operations on multiple items (e.g., disabling all alarms except one, updating multiple contacts), use a single loop in one code block rather than making individual API calls in separate steps. The rule [shr-00006] about writing small chunks means ensuring correctness before irreversible changes — it does NOT prohibit loops within a single code block. A loop over items with API calls inside is still a 'small chunk' as long as the logic is straightforward and verifiable.
[cms-00030] When performing time arithmetic (e.g., moving an alarm 1 hour later), always use programmatic calculation (e.g., Python's datetime module) rather than manual computation. This handles edge cases like midnight wrap-around (e.g., 23:30 + 1 hour should become 00:30, not 24:30). Parse the time string, add the delta with modulo handling, and format back to HH:MM.
[cms-00035] When parsing structured text content (e.g., note content with indented detail lines), be careful with string matching after calling `strip()`. After stripping, leading spaces are removed, so a line that originally started with `' - director:'` will now start with `'- director:'`. Always account for this by checking the post-strip prefix (e.g., use `line.startswith('- ')` not `line.startswith(' - ')`). When in doubt, print the stripped lines to inspect the actual format before writing matching logic.
[cms-00038] When a task specifies 'last N days including today' (or similar inclusive phrasing), today counts as one of the N days. Use `timedelta(days=N-1)` to calculate the start date, not `timedelta(days=N)`. For example, 'last 10 days including today' with today=June 2 means the window is [May 24, June 2], calculated as `today - timedelta(days=9)`. Using `timedelta(days=10)` would create an 11-day window. Always verify whether boundary transactions exist on the edge dates to determine if the off-by-one error actually matters.
[cms-00041] When identifying the 'last', 'most recent', or 'earliest' item from API results, always programmatically sort by the relevant timestamp field (e.g., `created_at`) using `sorted()` with a key and `reverse` parameter, rather than relying on the API's implicit return order or visual inspection of printed output. API return order is not guaranteed and may change. For example: `sorted(requests, key=lambda r: r['created_at'], reverse=True)[0]` to get the most recent item.
[cms-00042] When a task references 'this year' or 'released in this year', use `datetime.now().year` to get the current year programmatically. For Spotify's `release_date` field (format: '2023-04-29T08:00:31'), extract the year by slicing the first 4 characters and casting to int: `int(release_date[:4])`. Do not hardcode the year — always derive it dynamically from the system clock to ensure correctness across different task environments.
[cms-00046] When handling bill-splitting tasks that involve checking who has already paid, always resolve ALL participants to a unique identifier (email) FIRST before checking payment status. The correct workflow is: (1) parse the note to get all names and amounts, (2) look up each person's email via phone contacts, (3) fetch received transactions filtered by description and date, (4) match paid transactions by sender email against the set of participant emails using set operations, (5) request from the remainder. Do NOT visually match transaction sender names to note names — names may differ in format (e.g., 'Robin Burton' vs 'Robin') or be ambiguous.
[cms-00048] When a task says 'released after [year]' or 'after 2021 year', interpret this as strictly greater than that year (year > 2021, i.e., 2022 and later). Do NOT include songs released in 2021 itself. Similarly, 'before [year]' means year < year, and 'in or before [year]' means year <= year. Always clarify the boundary condition: 'after' is exclusive of the named year, 'in or after' would be inclusive.
[cms-00049] When a task references both 'the last/most recent' item AND a specific status/condition (e.g., 'the last payment request I sent was approved'), do NOT filter by status first and then find the most recent among the filtered set. Instead, fetch ALL items without the status filter, programmatically sort by timestamp to find the most recent, and then verify its status matches the expected condition. Filtering by status first risks missing a more recent item with a different status that the task implies should not exist but may exist due to data inconsistencies or edge cases.
[cms-00051] When filtering Venmo social feed transactions by participant involvement (e.g., 'transactions involving my roommates'), check BOTH the `sender` and `receiver` email fields against the target email set. A transaction 'involves' a person if they are either the sender OR the receiver. For example: `if sender_email in target_emails or receiver_email in target_emails`. Do not check only one role — this will miss transactions where the target person is on the opposite side of the transaction.
[cms-00052] When performing bulk operations on items identified by certain criteria (e.g., 'disable all alarms except the wake-up alarm'), always derive the target item IDs programmatically from the fetched data in code (e.g., `[a['alarm_id'] for a in all_alarms if a['alarm_id'] != wake_up_alarm_id and a['enabled']]`) rather than hardcoding IDs based on visual inspection of printed output. Hardcoding IDs read from printed output is fragile — if data changes between steps or output is misread, the wrong items could be modified or some items could be missed. Always maintain a clean data flow between steps by using variables from previous API responses.

## VERIFICATION CHECKLIST

[vc-00015] After performing bulk removals or modifications (e.g., cleaning up a library), re-fetch the affected data to verify the final state matches expectations. This confirms all changes were applied correctly and no items were missed.
[vc-00039] When verifying bulk removals, use the most efficient approach: re-fetch the affected data and simply check that none of the removed item IDs appear in the results. Do NOT re-fetch and re-check properties (e.g., release_date) for all remaining items — this wastes API calls. For example, after removing songs released <= 2021, collect the removed song_ids into a set, re-fetch the library/playlists, and assert that the intersection of removed_ids and remaining_ids is empty.
[vc-00044] Before performing bulk deletions of messages 'from' a specific phone number, print the `sender` and `receiver` fields of the fetched messages to verify direction. Confirm that all messages to be deleted have the target number as the `sender`, not as the `receiver`. This prevents accidentally deleting messages the user sent TO that number.
## TROUBLESHOOTING AND PITFALLS:

[ts-00025] When checking existing reviews/ratings for a user via `show_song_reviews` (or similar review APIs) with a `user_email` filter, do not assume there is only one review per user per item by just accessing `reviews_page[0]`. While typically true, if multiple reviews exist, you may miss subsequent ones. If the API returns multiple results, iterate through all of them or use `page_limit=20` and check the full list to ensure you are updating the correct review.

[misc-00009] When a task involves conditional logic (e.g., 'if already rated lower, increase to 5'), always check existing state before making changes. Use available filters (like `user_email`) to isolate the user's own records (e.g., reviews) rather than processing all records. Distinguish between create APIs (e.g., `review_song`) and update APIs (e.g., `update_song_review`) based on whether a record already exists.
[misc-00014] When dealing with conditional logic that spans multiple entities (e.g., 'an album is downloaded if all its songs are downloaded'), collect all necessary data from all related entities first (e.g., all downloaded song IDs), then apply the condition using set operations (e.g., `all(sid in downloaded_song_ids for sid in album_song_ids)`). Do not try to check conditions one item at a time without having the full reference set available.
[misc-00022] When asked to find the 'least recommended' or 'most recommended' artist/song/album, fetch all items from the relevant API (e.g., show_recommendations), count occurrences of each entity using collections.Counter, and find the entity with the minimum (or maximum) count. For artists specifically, iterate through each recommended song's 'artists' list and increment the count for each artist name.
[misc-00027] When calculating aggregate metrics across multiple parent entities (e.g., total duration per playlist), first collect all unique IDs across all parent entities into a set and fetch details once per unique ID (to minimize API calls). Then, when computing per-entity totals, iterate over each parent entity's original ID list (not the deduplicated set) to correctly handle duplicate items within a single entity (e.g., a playlist containing the same song twice).
[misc-00031] When a task requires following/adding/subscribing to entities (e.g., follow all artists from liked songs), always follow this idempotency workflow: (1) collect the full set of target IDs from the source data, (2) fetch the current state (e.g., currently followed artists) with pagination, (3) compute the diff using set operations (target_ids - current_ids), (4) perform the action only on the missing items in a single loop, and (5) verify the final state by re-fetching and confirming all target IDs are now present. This prevents redundant API calls and ensures idempotency.
[misc-00036] When a task says 'as per their request' or 'as requested', always examine the actual request message (e.g., text message, email) to determine specific filters, constraints, or preferences. Do not assume a generic interpretation. For example, if someone asks for 'movie recommendations from David Fincher' via text, 'as per their request' means filtering for David Fincher movies specifically, not returning all movie recommendations. Retrieve and read the original request message before acting.
[misc-00037] When parsing code returns an empty list or unexpected result, do NOT manually guess the answer from raw data as a fallback. Instead, debug the parsing logic by printing intermediate values (e.g., stripped lines, matched substrings) to identify the root cause. Manual fallback is fragile and unreliable for larger datasets, and it bypasses the verification that programmatic parsing provides.
[misc-00040] When you fetch detailed information (e.g., release_date via show_song) during the filtering/analysis phase of a task, always cache the results in a dictionary (e.g., song_details_cache[song_id] = song_info). Reuse this cache during verification or any subsequent logic that needs the same details, rather than making redundant API calls. This is especially important when verification requires checking the same properties you already retrieved.
[misc-00047] When creating Venmo payment requests (or similar irreversible bulk actions), always check for existing requests BEFORE creating new ones to ensure idempotency. Fetch `show_sent_payment_requests` filtered by description (if supported) or by recent date, collect the receiver emails of existing requests into a set, and only create requests for people whose emails are NOT already in that set. This prevents duplicate payment requests if the task is partially completed or re-run.
[misc-00053] When a task requires unfollowing/removing entities that do NOT meet a criterion (e.g., 'unfollow artists who haven't sung any liked songs'), use this inverse workflow: (1) collect the reference set of IDs from the criterion source (e.g., artist IDs from liked songs via `show_liked_songs` using `artists[].id`), (2) fetch all current entities (e.g., followed artists via `show_following_artists` using `artist_id`), (3) compute the complement: `ids_to_remove = {int(a['artist_id']) for a in followed_artists} - liked_artist_ids`, (4) remove each in a single loop, (5) verify by re-fetching and confirming the intersection of removed_ids and remaining_ids is empty. This is the inverse of [misc-00031] — instead of adding missing items, you remove items not in the reference set.
